# 運用手順書（お土産発注管理システム）

要件定義書 §4 非機能要件のうち、**バックアップ・データ保存期間・稼働監視・応答時間** を運用でどう満たすかをまとめる。

| 要件（§4） | この手順書での対応 |
|---|---|
| バックアップは1週間でフルバックアップ、1日単位で差分バックアップ | [1. バックアップ](#1-バックアップ) ・ `tools/backup_db.sh` |
| データ保存期間は6年目終了時に古いデータ1年分を削除して5年分を保持。削除対象は納品・返品処理が完了しているデータのみ | [3. データ保存期間（古いデータの削除）](#3-データ保存期間古いデータの削除) ・ `tools/purge_old_data.php` |
| 業務中は止まらない（平日 8:00〜20:00） | [4. 稼働監視](#4-稼働監視業務中は止まらない) |
| 応答時間を2秒以内 | [5. 応答時間の確認](#5-応答時間の確認2秒以内) |

本番環境は Railway（web サービス＋MySQL サービス）。DB 名は `omiyage_order`。

---

## 1. バックアップ

### 1-1. 方針（Railway Hobby プランで現実的なやり方）

| 種類 | いつ | 方法 | 保存先・保存期間 |
|---|---|---|---|
| フル | 毎週日曜 21:00（業務時間外） | `bash tools/backup_db.sh full`（mysqldump で全テーブル） | 管理PC＋別の保管場所（店の共有ドライブ等）。6週間分 |
| 差分 | 毎日 21:00（日曜以外） | `bash tools/backup_db.sh diff`（直近のフル以降に追加・更新された行） | 同上 |
| （あれば）ボリュームのスナップショット | Railway の自動スケジュール | MySQL サービスの Volume →「Backups」 | Railway 内 |

- **Railway の Volume Backups**：Railway ダッシュボードで MySQL サービスの Volume を開き「Backups」タブがあれば、手動・日次・週次のスナップショットを設定できる。
  ただし **プランによって使えない場合がある**ので、ダッシュボードで確認すること。使える場合も、これはボリューム丸ごとのスナップショットで、Railway の外には出ない（Railway 側の障害やアカウントの問題には弱い）。
  そのため、使える場合も **mysqldump のバックアップを Railway の外に置く**ことを基本にする。
- **差分バックアップの中身**：全テーブルに `updated_at`（更新日時。`ON UPDATE CURRENT_TIMESTAMP`）があるので、`updated_at >= 直近フルの開始日時` の行を `REPLACE INTO` 形式で取る。
  - 直近のフル以降の変更を毎回まとめて取る「差分（ディファレンシャル）」方式。復元は **フル1本 → 最新の差分1本** だけでよい。
  - **行の削除は差分に入らない**（未確定売上の上書きで消えた行、発注明細の削除、古いデータの削除など）。削除は次の週のフルで反映される。
    業務上、確定済みの伝票は削除しない（取消はマイナス明細で行う）ので、影響するのは未確定データだけ。
- **より厳密にしたい場合（参考）**：MySQL 8 はバイナリログ（binlog）が既定で有効なので、`mysqlbinlog --read-from-remote-server` で binlog を毎日取り出せば削除も含めた差分になる。
  ただし権限（REPLICATION SLAVE）・binlog の保持期間の確認・復元手順が難しくなるため、この規模では上の方式で十分とする。
- DB の容量は数MB程度なので、**毎日フルを取っても負担は小さい**。確実さを優先するなら「毎日フル（`full`）」でもよい（要件の「週1フル＋日次差分」も満たす）。

### 1-2. 準備（管理PC・最初に1回）

1. **MySQL クライアント**（`mysqldump` / `mysql`）を用意する。
   - 管理者権限が無い PC でも、MySQL 公式サイトの **ZIP 版（Windows (x86, 64-bit), ZIP Archive）** を展開すれば使える。`bin\mysqldump.exe` を使う。
   - XAMPP 付属（MariaDB）の mysqldump は、Railway の MySQL 8 の認証方式（caching_sha2_password）で接続できないことがあるので、MySQL 8 以降の公式クライアントを推奨。
2. **Git Bash**（`backup_db.sh` を動かす）。
3. **接続情報**：Railway の MySQL サービス →「Settings」→「Networking」で **Public Networking（TCP Proxy）** を有効にし、表示されるホスト名（`xxx.proxy.rlwy.net`）とポートを控える。
   ユーザー・パスワードは MySQL サービスの「Variables」の `MYSQLUSER` / `MYSQLPASSWORD`。
4. 接続情報はファイルに書いて **GitHub に上げない**（`.env` は `.gitignore` 対象）。例：管理PCの `C:\backup\okashi_env.sh`
   ```bash
   export MYSQLHOST=xxx.proxy.rlwy.net
   export MYSQLPORT=12345
   export MYSQLUSER=root
   export MYSQLPASSWORD='（Railway の値）'
   export DB_NAME=omiyage_order
   export BACKUP_DIR=/c/backup/okashi
   export MYSQLDUMP='/c/mysql/bin/mysqldump.exe'
   ```

### 1-3. 手動で実行する

```bash
cd /c/…/Okashi
source /c/backup/okashi_env.sh
bash tools/backup_db.sh full     # フル
bash tools/backup_db.sh diff     # 差分（フルが1回もないとエラー）
```

- 出力：`$BACKUP_DIR/omiyage_order_full_YYYYMMDD_HHMMSS.sql.gz` ／ `omiyage_order_diff_YYYYMMDD_HHMMSS.sql.gz`
- `last_full.txt`：直近のフルの開始日時（差分はここから後の行を取る）
- `BACKUP_KEEP_DAYS`（既定 42日＝6週）より古いファイルは自動で消える

### 1-4. 自動実行（Windows タスクスケジューラ）

タスクスケジューラは **ユーザー権限で作れる**（管理者不要）。「基本タスクの作成」で次の2つを作る。

| タスク名 | トリガー | 操作（プログラム／引数） |
|---|---|---|
| okashi_backup_full | 毎週 日曜 21:00 | `C:\Program Files\Git\bin\bash.exe` ／ `-lc "source /c/backup/okashi_env.sh && cd /c/…/Okashi && bash tools/backup_db.sh full >> /c/backup/okashi/backup.log 2>&1"` |
| okashi_backup_diff | 毎日（月〜土）21:00 | 同上で `full` → `diff` |

- PC の電源が切れていると動かないので、「スケジュールされた時刻にタスクを開始できなかった場合、すぐにタスクを実行する」にチェックを入れる。
- 毎週月曜に `backup.log` と、ファイルができているか（サイズが極端に小さくないか）を確認する。
- 管理PCが無い運用にする場合は、Railway に **Cron 用のサービス**（mysql クライアント入りのイメージで `backup_db.sh` を実行し、外部ストレージへ送る）を作る方法もある。
  ※ GitHub Actions でバックアップを取る方法は、このリポジトリが公開のため **成果物（Artifacts）を誰でも取得できてしまう** ので使わない。

### 1-5. 復元手順

> 復元は業務時間外（20:00 以降）に行う。復元前に、今の状態も念のため `full` で取っておく。

1. 使うファイルを決める：**復元したい日の直前のフル1本** と、**そのフルより後で、復元したい日までの最新の差分1本**。
2. 本番の Web を止めるか、利用者に操作しないよう連絡する。
3. フルを流す（`CREATE DATABASE` / `DROP TABLE IF EXISTS` / `CREATE TABLE` 入り。テーブルは作り直される）
   ```bash
   source /c/backup/okashi_env.sh
   export MYSQL_PWD="$MYSQLPASSWORD"
   gzip -dc omiyage_order_full_20270103_210000.sql.gz | /c/mysql/bin/mysql.exe -h "$MYSQLHOST" -P "$MYSQLPORT" -u "$MYSQLUSER"
   ```
4. 差分を流す（`REPLACE INTO` なので同じ主キーの行は上書きされる）
   ```bash
   gzip -dc omiyage_order_diff_20270106_210000.sql.gz | /c/mysql/bin/mysql.exe -h "$MYSQLHOST" -P "$MYSQLPORT" -u "$MYSQLUSER"
   ```
5. 確認：ログイン → メニュー → 在庫一覧・直近の発注／納品／売上が見えるか。件数を比べる：
   ```sql
   SELECT (SELECT COUNT(*) FROM t_order) 発注, (SELECT COUNT(*) FROM t_delivery) 納品,
          (SELECT COUNT(*) FROM t_sales) 売上, (SELECT MAX(updated_at) FROM t_stock) 在庫最終更新;
   ```
6. 注意：差分に削除は入らないため、フル以降に **削除した未確定データ** が復活することがある。未確定の伝票・売上を画面で確認し、不要なら削除する。
7. 別の DB 名に復元して中身だけ確かめたいときは、DB 名を置き換えてから流す（ローカル XAMPP での練習にも使える）。
   ```bash
   gzip -dc omiyage_order_full_….sql.gz | sed 's/`omiyage_order`/`omiyage_restore`/g' | mysql -u root
   gzip -dc omiyage_order_diff_….sql.gz | sed 's/`omiyage_order`/`omiyage_restore`/g' | mysql -u root
   ```

- 確認済み（ローカル MariaDB）：フル → データ変更 → 差分 → 別DBにフル＋差分で復元し、取引テーブル7つの `CHECKSUM TABLE` が元の DB と一致した。

## 2. バックアップの保管と確認

- 保管場所は最低2か所（管理PC＋共有ドライブ等）。バックアップには操作者のメールアドレスやパスワードのハッシュが入るので、**公開の場所（GitHub 等）に置かない**。
- 月に1回、最新のフル＋差分をローカル（XAMPP）に別名で復元し、画面が開けることを確認する（復元できないバックアップは意味がないため）。

## 3. データ保存期間（古いデータの削除）

### 3-1. ルール

- 年度は **4月1日〜翌3月31日** とする。
- **年に1回、年度が変わった直後（4月の最初の土日など、業務時間外）** に実行し、「今年度の開始日の5年前の4月1日」より前の伝票を削除する。
  例：システム開始が 2026年度 → 6年目（2031年度）が終わった 2032年4月 に実行すると、基準日は 2027/4/1。
  2026年度（1年目）の伝票が消え、2027〜2031年度の5年分＋今年度が残る。
- 削除対象は **納品・返品処理が完了している発注伝票とその納品・返品伝票だけ**（`tools/purge_old_data.php` の先頭コメントに条件を詳しく書いてある）。
  1. 発注が確定済みで、発注日が基準日より前
  2. 全明細の未納品数が 0（発注数＋取消数−確定済み納品数）
  3. その発注に対する納品・返品伝票がすべて確定済みで、納品日も基準日より前
  4. 取消明細でつながっている発注伝票、同じ納品伝票に入っている発注伝票も一緒に消せる
  → 条件を満たさない伝票（未納品が残っている・未確定の返品がある等）は **消さずに残る**。翌年以降、完了していれば消える。
- 削除しないもの：マスタ（商品・卸業者・操作者）、在庫（`t_stock`）、**売上（`t_sales`）・棚卸（`t_stocktaking`）**。
  要件の削除対象は「納品・返品処理が完了しているデータ」のため、売上・棚卸は対象外とした。
  売上・棚卸は1日×商品数程度の件数で、5年分でも数万行（数MB）なので保持しても性能上の問題はない。削除が必要になったら顧客と相談して対象・条件を決める。
- 未納品が何年も残っている発注は削除されないので、**発注取消（マイナス明細）で締めておく**と翌年に削除対象になる。

### 3-2. 手順

1. **フルバックアップを取る**（`bash tools/backup_db.sh full`）。このファイルは削除前の記録として **通常の6週間とは別に1年間** 保管する。
2. **確認（DRY-RUN）**：何も消さずに件数だけ表示する。
   ```bash
   php tools/purge_old_data.php              # 基準日は自動（今年度開始の5年前の4/1）
   php tools/purge_old_data.php --verbose    # 対象の発注No・納品Noも表示
   php tools/purge_old_data.php --before=2027-04-01   # 基準日を指定
   ```
   表示例：
   ```
   [purge] DB：omiyage_order　基準日：2027-04-01（発注日がこれより前の伝票が対象）　モード：確認だけ（DRY-RUN）
   [purge] 削除対象の件数
     t_order               120 件
     t_order_detail        480 件
     t_delivery            150 件
     t_delivery_detail     520 件
   ```
3. 件数が妥当か確認する（帳票の「発注明細表」「納品明細表」で基準日前の件数と比べる等）。
4. **削除**：
   ```bash
   php tools/purge_old_data.php --execute
   ```
   - 1トランザクションで、納品明細 → 納品 → 発注明細（取消明細 → 元明細）→ 発注 の順（FK の子 → 親）に消す。
   - 途中で失敗したり、数えた件数と消えた件数が違ったりしたら **全部元に戻して** エラー終了する（終了コード 1）。
   - 最後に各テーブルの残り件数を表示する。
5. 帳票画面で、残すべき期間のデータが見えることを確認する。

### 3-3. Railway での実行方法

どちらか。

- **A. Railway CLI でコンテナに入って実行**（`tools/` はコンテナに入っている。ブラウザからは開けない設定）
  ```bash
  railway ssh --service <web サービス名>
  php tools/purge_old_data.php            # DRY-RUN
  php tools/purge_old_data.php --execute
  ```
- **B. 管理PCから Public Networking 経由で実行**（PHP 8 と pdo_mysql が必要。XAMPP の php.exe でよい）
  ```bash
  DB_HOST=xxx.proxy.rlwy.net DB_PORT=12345 DB_USER=root DB_PASS='…' DB_NAME=omiyage_order php tools/purge_old_data.php
  ```

- 確認済み（ローカル）：古い日付のテストデータ（取消明細あり・返品あり・他の未完了発注と同じ納品伝票に入っているもの・未確定の発注から取消されているもの）で、
  削除すべき伝票だけが消え、それ以外は残ること、削除後に FK の孤立行が 0 件であることを確認した。

## 4. 稼働監視（業務中は止まらない）

### 4-1. Railway の設定（`railway.json`）

- `healthcheckPath: /index.php`（タイムアウト 120秒）：**デプロイ時**に新しいコンテナが応答するまで切り替えない（応答しなければ古いまま動き続ける）。
  ※ Railway のヘルスチェックはデプロイ時だけで、稼働中の常時監視ではない。
- `restartPolicyType: ON_FAILURE`（最大5回）：コンテナが異常終了したら自動で再起動する。
- Web サービスの設定で **Serverless（App Sleeping）がオフ** になっていることを確認する（オンだと、しばらくアクセスが無いと停止し、最初のアクセスが遅くなる）。
- **デプロイは業務時間外（20:00 以降・休日）に行う**。デプロイ中の切替えで数秒止まることがあるため。

### 4-2. 外部からの死活監視

- UptimeRobot などの無料の外部監視サービスで `https://<本番URL>/index.php` を **5分間隔** で監視し、止まったら管理者にメールが届くようにする。
- 監視の時間帯は平日 8:00〜20:00 が重要。朝 7:50 にも一度、ブラウザでログイン画面が開くか確認するとよい。
- 止まったとき：
  1. Railway ダッシュボードで web / MySQL サービスの状態とログ（Deploy Logs / HTTP Logs）を見る。
  2. web が落ちている → 「Restart」。直前のデプロイが原因なら、前のデプロイを「Redeploy」して戻す。
  3. MySQL が落ちている → MySQL サービスを「Restart」。Volume の容量不足でないか確認する。
  4. Railway 全体の障害 → https://status.railway.com を確認し、復旧を待つ（利用者に連絡）。

### 4-3. 利用料の確認

- Hobby プランは利用量の上限を超えると止まることがある。月に1回、Usage（利用量）を確認し、上限（Usage Limit）とメール通知を設定しておく。

## 5. 応答時間の確認（2秒以内）

### 5-1. 測り方

- **ブラウザ**：開発者ツール（F12）→「Network」→ 画面を再読み込み → 一番上（PHP のページ）の「Time」を見る。
- **コマンド**（ログイン後の Cookie を使って主要画面を測る）：
  1. ブラウザでログインし、開発者ツール →「Application」→ Cookie の `PHPSESSID` の値をコピー。
  2. 次を実行（`time_total` が秒。2 未満なら OK）：
     ```bash
     U=https://<本番URL>
     C='PHPSESSID=（コピーした値）'
     for p in /menu.php /order/order_input.php /delivery/delivery_input.php \
              /sales/sales_input.php /stocktaking/stocktaking_input.php /report/sales_list.php; do
       curl -s -o /dev/null -b "$C" -w "%{http_code} %{time_total}s $p\n" "$U$p"
     done
     ```
- 帳票の PDF 出力・メール送信（発注確定）は外部処理を含むので別に測る（メール送信は数秒かかることがある）。

### 5-2. いつ測るか・遅いときの対処

- リリース前、年度の古いデータ削除の後、利用者から「遅い」と言われたときに測り、結果を記録する。
- 2秒を超えたとき：
  - HTTP Logs で遅い画面を特定する。
  - 一覧・帳票は期間の絞り込みを短くして比べる（データ量が原因か）。
  - Railway の Metrics で CPU・メモリが張り付いていないか見る。
  - DB の同じリージョンに web があるか確認する（リージョンが違うと1回の問い合わせごとに遅くなる）。
